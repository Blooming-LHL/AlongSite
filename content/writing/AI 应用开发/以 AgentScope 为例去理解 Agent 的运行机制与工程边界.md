## 定义

AgentScope 是一个由阿里开发的构建模型驱动 Agent 应用的框架。它将消息表达、模型适配、工具执行、状态管理和运行流程组织成可以组合的组件，让开发者能够从一次简单对话逐步构建有工具、有记忆、可恢复、可观测的应用。

理解它的关键，在于分清模型能力与程序责任。
- 模型根据输入提出回答或工具调用请求；
- 框架组织状态和执行流程；
- 应用代码决定哪些能力允许执行、什么结果可信，以及何时能够保存和展示。
最终系统的可靠性由这几层共同决定。

## 心智模型

一次 Agent 回复，可以理解为围绕状态运行的控制循环：

```text
用户问题
  → Msg 表达输入
  → Agent 接收输入并更新状态
  → 组合本次模型可见的上下文
  → Formatter 转换消息，ChatModel 请求模型服务
  → 模型给出回答，或提出工具调用
       → 若有工具调用，Toolkit 执行并返回观察结果
       → 观察结果进入上下文，模型继续推理
  → 满足完成条件后返回 Msg
  → 应用校验结果
  → 保存与展示
```

这条链中，**信息流**决定模型看到了什么，**控制流**决定下一步做什么，**执行边界**决定工具能触及哪些资源。调试时只盯最终回答往往找不到原因，需要分别检查这三个层面。

例如，回答遗漏已知事实可能是信息没有进入模型上下文；工具反复调用可能是循环停止条件或错误反馈不清楚；工具访问了错误文件则可能是路径和权限边界有问题。它们表现为同一个“Agent 不好用”，但修复位置不同。

## AgentScope 中的实现

### 1. Msg：统一表达信息，保留作者与内容类型

`Msg` 是 AgentScope 内部保存和传递信息的基本对象。它把“谁说的”“以什么协议角色说的”“包含什么内容”放在同一结构中。

`name` 标识具体作者，例如 Assistant Alice、Assistant Bob 或 user；`role` 表示模型对话协议中的职责，例如 user、assistant、system。同为 assistant 的消息可以来自不同 Agent。Bob 接收到 Alice 的 assistant 消息后，消息作者仍是 Alice，协议角色也不会因接收方改变。

内容通过 ContentBlock 表达，既可以是文本，也可以是数据、工具调用和工具结果。AgentScope 2.0.5 版本对角色和内容类型有所限制：user 消息允许文本与数据，system 消息只允许文本。

因此，`get_text_content()` 是“提取文本”，而不是“判断消息是否完整或为空”。纯图片消息可以没有文本，但仍有数据内容。应用若先提取字符串再交给下游，会丢失非文本信息；模型适配和多模态处理应尽量保留原始消息结构。

### 2. Credential、ChatModel 与 Formatter：连接、调用和适配各有职责

Credential 保存模型凭证信息和服务端点，例如 API key 与 base URL。ChatModel 保存模型名称、调用参数、流式配置、重试等，并执行一次模型推理。Formatter 负责把统一的 Msg 转换为模型供应商要求的请求格式。

这种分工让 Agent 能使用相近的内部消息结构连接不同模型，但并不意味着所有供应商的请求格式相同。例如角色映射、多模态字段、system 消息和工具调用编码可能不同。Formatter 必须与 ChatModel 及其服务协议匹配；产生一个合法 Python 字典不代表服务端会接受它。

在 AgentScope 2.0.5 中，`OpenAIChatModel` 的默认生成参数通过 `OpenAIChatModel.Parameters` 配置。将 `temperature` 或 `max_tokens` 直接放到模型构造参数中会被拒绝；部分单次调用参数可以覆盖默认值。这提醒我们：参数属于认证层、模型配置层还是单次请求层，应按真实签名判断。

直接调用模型时，非流式返回完整 `ChatResponse`；流式返回需要 `async for` 消费的异步生成器。流式 chunk 可能是文本、工具调用增量或元数据，边界不固定，因此界面需要处理拼接、空块、结束、错误和中断，不能假设每个 chunk 都是一个字。

### 3. Agent.reply：将单次模型调用组织成有状态的回复过程

ChatModel 负责一次推理；Agent 负责接收输入、更新状态、组织模型输入、控制工具循环并形成最终回复。直接调用 ChatModel 通常得到 `ChatResponse`，通过 `await agent.reply(...)` 得到的是 `Msg`。

`reply` 是异步函数。调用 `agent.reply(message)` 只创建 coroutine，真正的执行需要 await 或任务调度。漏写 await 时，模型不会因为创建了 coroutine 就自动开始运行。

Agent 可以接收一条 Msg、多条 Msg 或 None。消息列表按顺序保存到上下文，然后整体参与推理；不意味着每条消息都对应一次模型调用。`reply(None)` 表示没有新的外部消息，Agent 仍可以依据已有历史和系统指令继续回复。

输入进入状态 agent.state、状态 agent.state 转换成模型输入、模型结果写回状态 agent.state，是 Agent 的三段基本工作。理解这三段，就能判断某条信息是在接收前丢失、构造上下文时被排除，还是模型回答后没有正确保存。

### 4. ReAct：模型提出行动，程序执行，再把结果交回模型

ReAct 的核心是 Reasoning 与 Acting 之间的反馈闭环。模型推理后可以直接回答，也可以生成 `ToolCallBlock`；Agent 根据调用请求执行工具，得到 `ToolResultBlock`，把结果交给下一轮推理。

```text
Reasoning → ToolCall → Acting → ToolResult → Reasoning → 最终回复
```

“观察”是下一次推理的输入，不保证模型一定成功纠错。循环必须有明确的停止、失败和等待条件，例如最终回复、迭代上限、权限确认、外部执行、中断以及模型调用失败。

🌰 在 AgentScope 2.0.5 中，`max_iters` 按内部动作计数，模型推理和工具执行都会消耗预算。一次“请求工具、执行工具、总结结果”的流程需要 3 次动作预算，而不是 2 次模型调用预算。所以配置迭代预算前，必须确认当前框架在计算“轮次”还是“动作”。

工具 `ERROR` 和权限 `REJECT` 也不同。前者表示执行产生失败观察，通常还可以继续推理；后者表示未获得执行权限，其停止策略由相应配置控制。把二者混淆会导致错误重试或不恰当的提前退出。

### 5. Toolkit：把 Python 代码变成模型可请求的工具

工具接入有两部分：向模型描述能力，以及根据模型请求实际执行。FunctionTool 从函数签名、类型标注和 docstring 生成名称、描述与输入 schema；Toolkit 管理工具，并处理查找、执行和结果汇总。

模型看到 schema 后提出调用请求。真正的 Python 执行发生在工具层，模型本身没有因此获得任意代码执行权限。函数结果可以被归一化为工具输出；需要明确状态、元数据、多模态内容或进度时，应使用框架的类型化结果结构。

工具设计还应做到输入明确、返回可读、范围有界。例如读取源码工具应限制根目录、路径、文件类型、页数和大小；模型建议的参数不能直接视为可信输入。

### 6. State、Memory、Context：保存了什么，不等于看到了什么

这三个概念重叠，但不能互换。

| 概念      | 关注的问题                       |
| ------- | --------------------------- |
| State   | Agent 当前运行状态是什么，哪些状态可以保存恢复？ |
| Memory  | 历史信息如何保存、压缩、检索和再次利用？        |
| Context | 这一次模型调用实际看到了哪些信息？           |

学习使用的内置 Agent 以 `state.context` 保存尚未压缩的对话，以 `state.summary` 保存旧上下文摘要。完整模型输入还包含 system prompt；工具 schema 则通过工具参数提供。State 还包含当前回复、工具及中间件等运行状态，因此它不只是聊天记录。

上下文压缩把旧消息归纳成摘要，保留部分近期原始消息，降低后续输入体积和溢出风险。代价是额外摘要调用和信息损失。精确错误字符串、路径、关键决策等应特别保留；必须逐字保存的信息应另存到可靠存储中。压缩后若没有足够多的后续调用，总成本也不一定下降。

### 7. 结构化输出：约束数据形状，还要验证内容依据

自然语言适合人阅读，结构化结果适合程序处理。通过 Pydantic schema，可以要求必填字段、限定类型和范围、拒绝额外字段，使无效输出能够被检测。

通过对 AgentScope 2.0.5 的学习实验观察到：传入 `structured_schema` 后，Agent 注册内置结构化输出工具，校验模型提交的数据；校验失败形成错误工具结果，下一轮推理可以修正；成功数据最终出现在 `Msg.structured_output`。

但 schema 只说明数据满足形式约束。一个合法的路径、行号和引文字段仍可能是伪造的，一个结构完整的解释也可能不受证据支持。因此实际应用应分层检查：先验证形状，再验证来源和业务约束，必要时再进行语义评估。

### 8. Middleware 与执行环境：管理横切逻辑和资源边界

❗️AgentScope 中的 Middleware 的概念和常见概念不一样，这里主要是指提供 Agent 执行过程中的 log、tracing 等能力

Middleware 用于在不修改 Agent 核心实现的情况下观测或改变运行过程；Hook 是它接入生命周期的位置，`next_handler` 表示继续执行下一层。注册 A、B 时，典型顺序是 `A.before → B.before → core → B.after → A.after`。

普通 after 逻辑可能被异常跳过。可靠清理应放在 `finally`，而是否处理或重新抛出异常需要另行决定。审计、模型调用统计和统一错误处理放在合适的生命周期位置，才能覆盖未发生工具调用的回复过程。

执行环境则回答另一个问题：工具实际在哪台机器、哪个目录和什么权限下运行。Workspace 提供文件与命令操作环境；Offloader 承载被卸载的大内容。隔离环境中的读写挂载仍可能修改宿主目录，因此“在容器或沙箱里”不能代替资源权限分析。

中断和外部执行需要保持状态闭环。课程实验验证了，尚未结束的工具调用在中断后应获得同 ID 的终态结果，使等待状态清除。仅停止执行而留下悬空 ToolCall，会影响后续恢复与模型输入一致性。

### 9. Session：恢复状态时，也要重建运行依赖

会话持久化应把会话身份、可序列化状态和运行依赖分开。session ID 用于定位记录；状态包含需要恢复的数据；模型、Credential、Toolkit、Workspace 等对象通常需要重新创建。

🌰 在练习中，使用 `AgentState.model_dump_json()` 保存状态，再用 `model_validate_json()` 恢复。跨进程实验保留了消息、回复 ID 和迭代字段；把无编码规则的 `object()` 放进状态后，保存阶段直接失败。字段类型是 Any，并不保证任何 Python 对象都能转换为 JSON。

恢复失败可以按顺序检查：是否找到了正确会话，持久化数据是否能够校验，以及运行时工具和模型是否重建完整。业务应用也可以选择只保存已验证问答，而不是完整 AgentState；保存边界应由后续需要恢复的语义决定。

### 10. 多 Agent：消息传递决定协作，编排决定责任

多个 Agent 各自持有状态，默认不会共享完整上下文。`observe` 接收并保存消息，不调用模型；`reply` 接收消息后继续推理。传给 Bob 一条 Alice 的回复，只会让 Bob 收到那条消息。

广播把消息交给当前参与者，却不负责选择下一位发言者。发送者已经保存自己的回复，广播通常需要排除发送者；接收者已 observe 后用 `reply(None)` 可以避免重复输入。成员加入和移除只改变之后的信息范围，无法撤回已收到的敏感消息。顺序广播中途失败，还可能造成只有部分成员收到消息。

并发只适合没有数据依赖的节点。gather 返回结果保持输入顺序，默认首个异常不自动取消兄弟任务；TaskGroup 会在子任务异常时取消其他任务并完成清理。需要保留超时前部分结果时，可以使用 `asyncio.wait` 分开处理 done 和 pending，再取消并等待剩余任务。

编排选择取决于责任关系：固定步骤适合 Pipeline；按条件选择分支适合 Routing；处理中转移任务责任适合 Handoff。规则足够明确时，普通代码路由往往更容易验证。额外 Agent 会增加调用、延迟和失败点，应通过质量评估证明收益。

### 11. MCP、Skill、RAG 与长期记忆：扩展不同层面的能力

本地函数执行当前进程中的能力；MCP 提供跨进程或远端工具发现与调用协议；Skill 提供操作说明和配套资源。它们分别解决执行、连接和行为指导问题。Skill 中有脚本不表示 Agent 自动获得执行权限；MCP 工具白名单限制可见能力，也不能代替服务端数据范围与参数校验。连接和 transport 还需要正确关闭。

RAG 与长期记忆也有不同目标。RAG 从外部知识库检索与问题有关的文档证据；长期记忆保存跨会话仍有价值的用户和任务事实。检索结果的分数表示相似度，来源、版本、状态和生效时间才决定证据能否使用。

检索返回空列表时，由应用决定确定性拒答；把空证据交给模型自由补全，会失去“基于来源回答”的边界。

### 12. 测试、Tracing 与 Evaluation：三种不同的验证问题

确定性测试判断代码是否满足契约，例如工具是否拒绝越界路径、失败是否不写入 session。Tracing 记录一次调用经过的步骤、时间和状态，帮助定位故障。Evaluation 在一组样本上衡量回答质量和业务收益。

三者不能互相替代。工具测试通过不代表模型解释正确；span OK 不代表工具业务成功；评估集成绩高也不能证明每个安全分支都正确。测试替身适合重复验证流程，真实模型评估用于检查语义行为，两者应分别保留证据。

评估指标必须反映产品目标。如果为了提高回答成功率而放宽引文校验，系统可能更容易给出回答，却更容易放行伪造来源。应同时观察首次成功率、最终成功率、错误放行、重试、耗时与成本。

## 最小示例

### 利用上述所学做一个“代码训练教练”的 MVP

#### 背景信息：
做一个可以帮助用户学习代码项目的教练 Agent

#### 具体实现：
用户输入是一个关于当前项目源码的问题。应用创建带两个有界只读工具的 Coach：一个列出允许的项目文件，一个分页读取允许的源码。每次读取保留请求内证据快照，记录实际交给模型的行范围。

Coach 使用这些证据生成结构化草稿，包含回答状态、解释、引文和回忆题。应用检查引文是否来自实际读取范围、文本是否逐字一致。只有 `answered` 进入 Reviewer，由它判断解释是否受到已核验引文支持；证据不足直接返回。

```text
用户问题
→ Coach + 只读工具
→ 结构化草稿
→ 引文确定性校验
→ answered 时进入 Reviewer
→ 展示前复读源文件并比较字节
→ 通过后原子保存会话、展示回答
```

Reviewer 拒绝后，新的 Coach 最多重新生成一次；再次拒绝或复核异常就停止。未通过结果不写入历史，避免污染下一轮上下文。旧问答可以用于理解指代，但不作为新回答的源码证据。

#### 设计思想：
这个例子体现了各层的分工：AgentScope 负责消息、模型、工具循环和结构化输出；应用负责路径策略、证据真实性、源变化检查、有限重试和提交时机；Reviewer 提供额外的概率性语义检查。

## 常见误区

这些课程共同纠正的，是把相邻概念当成同一件事：

- 文本提取成功，不代表保留了完整消息；格式化成功，不代表模型服务接受请求。
- 直接模型调用，不等于 Agent 完整运行；创建 coroutine，不等于异步逻辑已执行。
- 工具业务 ERROR，不等于权限 REJECT；trace span OK，不等于回答正确。
- State，不等于全部记忆；state.context，不等于本次模型的全部输入。
- 结构化输出通过，不等于引文真实；Reviewer 接受，也不构成正确性保证。
- 广播，不等于调度；多个 Agent，不等于共享上下文；并发节点，不应有未满足的数据依赖。
- Skill 指令，不等于工具执行权限；工作区隔离，不等于读写挂载不会影响宿主资源。
- 保存状态，不等于保存了所有运行对象；恢复会话，还需要重建模型和工具。
- 高相似度，不等于文档仍然有效；小型评估集通过，不等于生产可靠性。

学习框架时，最有用的能力是能够解释每个边界，并用小实验验证它。API 名称会随版本变化，但消息、状态、执行、证据和控制流之间的关系，可以帮助我们在新版本中重新定位实现。
